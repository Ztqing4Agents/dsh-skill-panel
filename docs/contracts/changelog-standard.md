# CHANGELOG 编写规范：结构、分类边界与写作风格

> 类型：规范
> 读者：要往 `CHANGELOG.md` 里记一条变更的人；给某一版写 Release 正文、需要回查条目事实的人
> 真源：2026-11-28 用户拍板的体例，本文件即体例原文；条目事实的唯一出处是 `CHANGELOG.md` 自身，结构由 `scripts/check-docs.mjs`（R6）与 `scripts/check-docs-standards.mjs`（G6）两处守
> 更新触发：改结构、改分类边界、改写作风格，或改这两道结构门禁的覆盖范围时，同轮改本文件
> 规模上限：400

本规范定义 `CHANGELOG.md` 的结构、分类边界、写作风格与门禁约束，并与《Release 文档编写规范》（`docs/contracts/release-doc-standard.md`）形成清晰分工：Release 负责 **10 秒扫读的重点摘要**，`CHANGELOG.md` 负责 **完整、精准、可追溯的版本变更档案**。

## 10.1 与 Release 文档的分工

| 维度 | `CHANGELOG.md`（变更日志） | `docs/releases/` 下与 tag 同名的逐版正文（发布说明） |
| ----- | ----- | ----- |
| 定位 | 项目全生命周期的**完整变更档案**（单一真源） | 面向单次发版的**精炼发布摘要** |
| 分类标题 | 严格遵循 Keep a Changelog 英文六类（`Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`） | 面向用户的中文分类（`破坏性变更` / `新增` / `改进` / `修复` / `移除`） |
| 信息粒度 | 记录全部可感知变更、精确参数/版本区间、行为前后对比与迁移步骤 | 只提炼重点与必做动作，每条 1 句话，不展开细节 |
| 覆盖关系 | 最全，含 `[Unreleased]` 未发布区与历史版本（含 `0.1.0`） | 仅覆盖正式发布版本，事实不得超出 `CHANGELOG.md` |

## 10.2 结构与门禁硬约束

必须严格遵守 [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/) 与 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/)，以通过 `check:docs`（R6）与 `check:docs:standards`（G6）：

1. **顶部固定**：一级标题 `# Changelog`，附简短说明与 Keep a Changelog / SemVer 链接。
2. **未发布区置顶**：`## [Unreleased]` 必须位于所有版本之上，用于暂存尚未发版的改动。
3. **版本标题格式**：严格为 `## [x.y.z] - YYYY-MM-DD`（不带 `v` 前缀；撤回版本可在末尾加 `[YANKED]`），按版本号倒序排列。
4. **分类白名单**：三级标题只允许使用官方六类英文：`### Added`、`### Changed`、`### Deprecated`、`### Removed`、`### Fixed`、`### Security`；无内容时不写空节。
5. **文末对比链接**：为 `[Unreleased]` 及每个已发布版本维护 GitHub Compare 引用链接，首版指向 `releases/tag/v0.1.0`（`0.1.0` 是 `private: true`、未发 npm 的私有首发版，但仍然打了 tag，所以有可指的目标）。

## 10.3 分类判定标准

| 分类 | 归入标准 | 常见误判纠正 |
| ----- | ----- | ----- |
| `Added` | 用户此前完全没有的新功能、新交互入口、新支持的能力 | 市场页新增「原地更新」入口属 `Added`，不应归入 `Changed` |
| `Changed` | 既有功能的行为调整、默认策略变更、兼容范围变动、视觉/协议/本地化调整 | 破坏性变更仍归对应类别（通常为 `Changed`），但必须在主题前加 **`【不兼容】`** |
| `Deprecated` | 计划淘汰但当前仍可用的功能或配置 | 仅记录已明确弃用的能力，不写模糊预告 |
| `Removed` | 正式下线或删除的功能、路由、界面入口 | 同步说明替代方式（如有） |
| `Fixed` | 缺陷修复、报错解决、展示异常修正 | 同一条日志不混写「行为变更」与「缺陷修复」 |
| `Security` | 安全漏洞修复或安全边界加固 | — |

## 10.4 写作规范：骨架、语气与技术标识

1. **统一骨架**：

   * 一级条目：`- **核心主题**：具体说明（行为变化前后的差异、精确规格或影响范围）。`
   * 破坏性变更：`- **【不兼容】核心主题**：说明受影响范围、旧版本指引与必做动作。`（凡涉及包名变更、数据目录迁移、宿主最低版本抬升，一律强制标注 `【不兼容】`）。
   * 二级缩进子项：仅用于**大版本按模块分组**，或补充**升级步骤 / 旧宿主指引 / 关键边界条件**；**不用来解释设计动机或内部实现原理**。

2. **语气与视角**：

   * 保持**书面、克制、客观**的第三方记录语气，面向使用者与升级者。
   * 不写研发过程、内部实现与排期说明（如「普查 400 行」「改数据形状本轮未做」「不猜一个版本出来」「区间里不写出 tuple」）。
   * 不写无追踪依据的将来时承诺（如「待后续重新开放」「将来再支持」）。

3. **技术标识与数字**：

   * 包名、命令、路径、配置键、错误码、版本号与区间一律使用反引号。
   * 写明**稳定的规格数字**（如单文件上限 `8 MiB`、宿主区间 `>=0.2.3-0 <0.3.0-0`、图标尺寸 `36×36`），不把**会随时间腐化的动态统计数**（如上游市场某天的技能总数「22.4 万」）写死进条目。
   * 避免 Markdown 链接与反引号套用错误（如反引号内直接写纯 URL，不再叠一层 Markdown 链接语法）。

## 10.5 正反例对比

| 类型 | 示例 |
| ----- | ----- |
| 不推荐（口语化 + 研发独白） | `- **失败各有各的说法，目录与记录对不上时会补读一次**：后两种还会重读一次已安装列表——它们描述的正是目录与台账已经对不上的处境；回滚不必重读，那时磁盘与台账本就一致。` |
| 推荐（书面克制 + 面向用户） | `- **失败分级提示与状态校准**：更新失败时明确区分已回滚、目录已丢失与结果无法确认三种状态；后两种情况会自动重读已安装列表以同步实际状态。` |

## 10.6 标准模板

```
# Changelog

本项目的所有重要变更都将记录在此文件中。

格式基于 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，版本号遵循 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/)。

## [Unreleased]

## [x.y.z] - YYYY-MM-DD

### Added

- **新功能主题**：说明新增的能力、入口与关键规格。

### Changed

- **【不兼容】破坏性变更主题**：说明不兼容范围与影响。
  - **迁移步骤 / 旧宿主指引**：给出可直接执行的命令或旧环境应停留的版本号。
- **行为调整主题**：说明调整前后的具体变化。

### Fixed

- **修复问题主题**：说明原缺陷现象与修复后的表现。

[Unreleased]: https://github.com/Ztqing4Agents/dsh-skill-panel/compare/vx.y.z...HEAD
[x.y.z]: https://github.com/Ztqing4Agents/dsh-skill-panel/compare/vPrev...vx.y.z

```

## 10.7 验收

结构由两道门禁机械守，分类归属与措辞只能靠 review。

- **R6（`node scripts/check-docs.mjs`，只管仓库根的 `CHANGELOG.md`）**：首个一级标题必须是 `# Changelog`；`## [Unreleased]` 在场；每个 `## [` 版本的标题逐字合 `## [x.y.z] - YYYY-MM-DD`（可带 `[YANKED]`）；`### ` 分类头只许六类英文；必须存在 `[Unreleased]:` 对比链接定义行——缺了它（哪怕整块对比链接都没写）即红，因为正文里的 `[Unreleased]` 会在 GitHub 上渲染成原样方括号。
- **G6（`node scripts/check-docs-standards.mjs`，交付前的第二意见）**：`## [Unreleased]` 存在、版本标题形态（连漏写方括号的 `## 1.2.0` 也抓）、类别白名单。与 R6 交叉覆盖，任一道红都不许发版。
- **逐版正文的锚点会被反查**：`test/release-docs.test.mjs` 按 `CHANGELOG.md` 的 `## [x.y.z] - YYYY-MM-DD` 反算锚点，与 `docs/releases/` 里那份正文的 CHANGELOG 链接比对——改一个发布日期、或删掉某一节的版本标题，那条用例立刻红。
- **不覆盖什么**：条目该归哪一类、一句话是否说得准、数字是否会腐化、文末链首是否真是上一版，门禁都不判——这些是 review 的活；链接点开 404 只有人会发现。
- **自检顺序**：`node scripts/check-docs.mjs` → `node scripts/check-docs-standards.mjs` → `npm test`；改的是历史节而非 `[Unreleased]` 时，把 `test/release-docs.test.mjs` 一并看过再提交。
